## 原因和修复

- 批次随机 ID 曾直接进入 system，且“批量输出契约”标记无法通过原 cachedMessages 的识别条件。现在输出 schema 固定，ID 留在动态后缀，所有批次进入同一布局。
- 旧布局把固定消息规则、完整契约放在 history/state 后面。现在全局任务规则及消息规则固定在 system，user 按布局版本、世界设定、人物资料、契约、动态上下文排列。场景契约含动态阶段参数时也不会破坏前面的世界/人物前缀。
- 人物 createdAt/updatedAt 等元数据保留在动态部分；世界只提取明确列举的固定字段，未列字段完整留在后缀。未增加全世界角色名单、跨会话私信或外部知识。
- 统一对象键的代码点排序；无序实体数组按 ID/内容确定排序，历史数组保留原顺序。批次共享检测也使用确定序列化，避免对象插入顺序导致重复发送。
- 私密分组规则未放宽。批次要求同一实际任务规范；队列比较相关规范文本，不再因无关 Prompt 的全局版本/更新时间变化拆批。
- 布局版本为 2；不把全局更新时间、随机哈希或统一设定版本放在所有请求开头。真实内容变化自然失效该位置之后的前缀。没有添加填充、预热请求或改变并发上限。
- 缓存布局与 thinking 参数支持解耦；官方 DeepSeek 端点和已明确声明的兼容代理，在未知模型/参数回退时仍应用布局。stablePrefix=false 仍可关闭。
- 修复请求的前两个消息也使用该布局，后续修复指令完整保留。
- 紧凑协议保留精确消息数量、禁止重复和最早偏移约束。原实现替换契约时会丢弃追加约束，现作为 input.plannedConstraints 传递。
- packRequest 不再随 tight 档截短人物设定和关系经历，避免前缀抖动或人物信息损失；承诺/秘密等关键记忆不会被普通条数上限挤掉。必要事实超过预算明确报错，须提高预算，不能靠删设定获取命中率。

## 统计与复用

`src/ai/cache-statistics.ts` 提供全局、世界、任务分组以及两个账本的比较。仅接受非估算、非负整数且 hit + miss = input 的实际计数。整体数据不完整时 overallHitRate 为 null，同时给出 measuredHitRate 与覆盖请求数；零 Token 分母不产生比例。失败/截断请求只要有实际 usage 也计入。

输入费用使用每次请求保存的价格快照和汇率，以实际 hit/miss 分开计价；总费用另外计 output，reasoning 不重复相加。缺计数/价格时返回 null，不使用硬编码现价。这里是实际用量乘配置价格的成本计算，不冒充账单金额。用量页面支持显示/导出统计；其现有世界/任务筛选仍生效。

```sh
node scripts/compare-cache-runs.mjs before-backup.json after-backup.json report.json
```

输入是 usageLedger 数组或含 usageLedger 的完整备份。脚本不发 API 请求，不导出 Prompt 或密钥。

付费 A/B 仍须执行：从同一 100 人狂欢模式初始快照创建两个隔离数据库，固定种子、七虚拟日、观察范围、模型、价格、输出预算、消息和事件计划、上下文预算及调度速度；分别运行修改前后版本并保留各自完整账本。不能拿“关闭缓存布局”冒充本次修改前版本（旧版已经有部分布局）。冷启动、自然热缓存与重试均应纳入；不能额外预热刷请求。比较时核对计划完成数、对白数、事件数、验证拒绝数及私密知识，不能只比较 Token。服务端无法由客户端清空缓存，应记录先后顺序和间隔；实时分支内容会不同，固定请求序列实验与全模拟实验需要分别报告。

## 回归证据与限制

- 新测试覆盖 100 角色 × 7 天 × 16 任务的布局稳定性、无关规范编辑、静态设定、时间序列、批次隐私、修复路径、消息配额和真实计数的加权统计；这是离线结构测试，不是 100 人七日付费模拟。
- 真实七日归档回放通过：100 人、24 团体、3538 条线上消息、56 条线下对白、8 场景、9 重大事件；文本/角色/时间身份保持不变。回放不是重新生成内容或质量实测。
- 构建通过；缓存/上下文/Provider/Prompt/归档专项 69 项通过，追加批处理回归 3 项通过（包含相同计划的 5/20/50 人消息及场景数量验证）。批处理回归发现并修复了持久化任务只有空壳快照时的规范比较问题，现读取权威快照，未遗留该失败。完整测试首次运行 281 通过、5 失败：两项数据库旧版本断言（期望 15，工作区为 16）；活跃度测试一项 120 秒超时，另两项狂欢调度断言失败。没有修改这些调度/数据库实现来掩盖测试失败，不能宣称全量验收通过。

## ≥90% 的瓶颈

DeepSeek 官方文档说明缓存是 best-effort，需要已持久化的完整前缀单元；公共前缀检测、请求边界和固定间隔影响实际持久化，构建需要数秒，也可能被清理。并发首轮请求、角色轮换、关系/记忆变化、不同阶段契约及短请求会留下不可复用部分。客户端不能保证 90%。

即使稳定部分全部命中，若每次必须新增的输入超过总输入的 10%，且没有可复用的更长历史前缀，就无法仅靠静态设定达到 90%；首轮未命中会进一步拉低七天整体比率。这是结构条件，不是本项目的实测上限。输入费用下降也不等于总费用同比下降，输出费用仍然存在。
