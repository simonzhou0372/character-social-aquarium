# 线上—线下统一剧情线

## 问题

旧版本里，线上聊天和线下场景是两条独立流水线：

- 生活规划器每小时抽样一次「共同活动」，再由场景采样器按天数和概率决定是否生成场景；
- 聊天调度器独立挑选会话、发言者和话题，提示词里只有聊天历史、角色记忆和当前活动；
- 线下场景提示词里只有主事件、参与者和私有记忆，看不到参与者此前在线上说过什么；
- 场景生成后没有把对话写回参与者记忆，只有一行「某人和某人在某地」的占位记忆。

结果是：用户可能在同一天读到「两人在群里约好见面」「其中一人和第三人在私聊」「两人在线下咖啡馆」三段毫不相干的内容，而且第二天角色完全不记得咖啡馆里发生过什么。技术上每个服务都正确，叙事上却是断开的。

## 设计：以真实生活事件为锚的剧情线

新增 `src/core/storyline.ts`，把一次多人共同活动定义为一段剧情线的锚点：

```
lead  线上约定 / 期待   messages.eventId = event.id, simAt < scene.start
scene 线下共同经历      scenes.eventId = event.id
follow 线上回味 / 回应  messages.eventId = event.id, simAt >= scene.end
```

关联不使用「时间相近」猜测，而是复用真实外键：

- `Message.eventId` 指向生活事件；
- `InPersonScene.eventId` 指向同一生活事件；
- `InPersonScene.sourceConversationId` 记录这条线主要发生在哪个会话；
- 场景回顾记忆使用与调度器占位记忆相同的 `memory:${eventId}`，后写入的完整回顾替换占位内容。

因此重跑、补跑、备份恢复和时间回退后，关联仍然成立。

内置的《最后七天》等旧存档写于 `Message.eventId` 之前，消息与场景之间没有外键。首页剧情线会退回到「同一批人、场景前后数小时内的线上消息」来生成候选关联，并以「同期线上」标注；新生成的内容始终优先使用真实 `eventId`，不会把推断当成精确事实。

## 调度：带依赖的三段式任务链

当某个多人活动被场景采样器选中时，`core/engine.ts` 不再只入队一个场景任务，而是入队：

```ts
story:lead:<eventId>    // kind=chat,  at=event.start-18~55min
scene:<eventId>         // kind=scene, dependsOn=[lead]
story:follow:<eventId>  // kind=chat,  at=event.end+15~90min, dependsOn=[scene]
```

要点：

- **会话选择**：三人以上优先使用包含全部参与者的群聊，否则使用关系最紧密的一对一私聊；同分按稳定 ID 排序，保证重跑确定。
- **发言者**：优先使用关系上更主动的一方发起约定，另一方在场景结束后回应；只选择用户没有接管的角色。
- **可发言判断**：共同活动期间所有人的 `phone` 都很低，因此不能复用活动内的手机可用度。剧情线改为判断约定/回味发生的那个时刻角色是否醒着、是否有手机习惯。
- **回填时间**：共同活动通常正好从一个整点开始，约定必须落在上一段。允许写入 `simAt` 略早于当前检查点的消息，展示顺序按虚拟时间排序；`backfilled` 标记保证持久化不会把它当作乱序错误。
- **失败隔离**：场景会等待约定任务；但如果约定连续失败 3 次，场景仍可仅凭已确认的生活事件生成。回味任务必须等待场景完成，不会对着不存在的场景硬写反应。
- **幂等**：三个任务使用稳定 ID；已存在的任务不会重复入队，重放不会产生重复消息或重复场景。

快速补全（单 Agent）路径在同一个 JSON 响应里同时产出 `chats` 和 `scenes`，提示词要求同一 `eventIndex` 的线上与线下互相承接；提交时同样写入场景回顾记忆。

## 生成上下文：双向可见

### 线下场景看得到线上

`ai/scenes.ts` 在生成场景前调用 `sceneChatContext()`：

- 只收集**场景参与者共同在场**的会话，避免把某人与局外人的私聊带进场景；
- 取见面之前 8 小时内的最近消息；
- 单独取出 `eventId` 相同的线上铺垫 `linkedChat`；
- 作为 `input.recentChat / linkedChat / continuity` 注入阶段规划与每个阶段的请求。

系统契约明确要求：线上已确认的约定、地点和情绪必须被承接，但不要逐句复述，也不得与线上事实矛盾。

### 线上聊天看得到线下

`ai/orchestrator.ts` 的 `dialogueContext()` 新增 `input.story`：

- `happeningNow`：说话人此刻正在参与的线下场景；
- `justHappened`：最近 36 小时内结束、且与当前会话双方共同相关的场景；
- `priorOnline`：同一事件的线上前置消息；
- `note`：告诉模型当前是「约定前 / 正在见面 / 见面后」，以及应该怎样衔接。

`dialogueContract()` 增加了对应约束：不能各说各的，不能凭空发明场景细节，正在见面时不要像独自在家一样长聊。

## 记忆：线下经历进入角色的记忆

`sceneRecapMemory()` 从场景阶段中抽取最多 10 条关键对白/活动说明，生成一条参与者共享的 `episode` 记忆，包含：

- 场景标题、地点；
- 带发言人姓名的关键内容；
- 线上约定摘要（若有）；
- `eventId`、`at = scene.end`、`owners = scene.participants`。

写入时机：

- 普通生成：`generateScene()` 每次保存阶段时同步写入（幂等）；
- 场景完成：`engine.ts` 提交生活事件时不会用一句话描述覆盖已有的场景回顾；
- 快速补全：提交场景后立即写入。

因此下一次线上聊天通过既有 `retrieveMemories()` 就能检索到这段共同经历。

## 用户看到什么

- **首页新增「剧情线」区块**：同一段经历被放在一张卡里，按「线上约定 → 线下见面 → 线上回味」横向/纵向串联；点击线上节点进入会话，点击线下节点打开场景详情。
- **聊天页场景入口**：如果该场景有线上铺垫，入口文案变为「角色在线上约好后相聚」；若之后还有线上回应，额外显示「之后线上聊起」。
- 时间轴与线下观察保持原样，场景仍是完整档案。

## 验证

`tests/storyline.test.ts` 覆盖：

- 事件标记消息被正确分为 lead / scene / follow；
- 回顾记忆包含标题、参与者和线上约定；
- 群聊优先、私聊兜底的会话选择；
- 调度器确实产出 `lead → scene → follow` 依赖链；
- 完整 drain 后线上前置与事后消息都存在、场景记忆包含场景标题；
- 场景请求上下文包含线上铺垫，回味请求上下文包含线下场景。

## 边界

- 剧情线不是新的世界事实来源。AI 只能补充既定时空中的描述与对白，不能新增事件、改变参与者或改写关系。
- 不是每个多人事件都会成为剧情线：仍受场景采样比例、每日上限、观察范围和恢复预算约束。
- 观察范围之外的会话不会被拉进剧情线；`chooseStoryConversation()` 只使用当前观察范围内可调度的会话。
- 线上约定属于「先规划、后补写」，其 `simAt` 可能早于生成时刻；这是有意的回填，界面按虚拟时间展示。
- 若模型对约定任务连续失败，场景会退化为无前置的独立场景，而不是永久卡住。
