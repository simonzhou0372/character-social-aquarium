# 请求效率专项（2026-10-28）

本轮在工作区既有缓存、队列与紧凑协议修改上增量实现，未覆盖其他未提交工作。

## 审计与实现

- 请求出口集中在 `budgetedCompletion` → Provider。聊天（含修复）、生活描述、批量聊天/事件/线下阶段、旧线下生成、记忆、关系整理、重大事件、人物演化、报告、世界扩展/草稿、小说配置及连接测试均已静态定位。
- 最直接浪费：普通速度（<300）强制单任务，多个已就绪任务重复发送相同规则和上下文。现在普通速度也允许最多4个已就绪任务；不等候凑批，不改变计划或活跃度。已有输出预算、健康退避、上下文上限仍生效。
- 提取可测试的批次封装，相同输出契约提升为 sharedContract；不同契约仍在任务内部保留。共享事实继续仅抽取完全相同字段，聊天继续要求相同发言者、受众与授权知识，依赖任务必须等前置完成。
- 原封装动态 batchId 位于共享事实之前。现在共享事实/契约先于动态ID；DeepSeek缓存序列化也采用此顺序，保留既有稳定世界/人物前缀。未声称实际命中率已提高。
- 线下场景沿用本地阶段计划和原对白配额，同样获得低速合批；补充顺序承接与私有认知约束。重大事件存在因果和状态提交依赖，未强行跨事件合批。
- 概率抽样、活动状态、日程和线下阶段已经在本地执行；未将确定性工作重新交给模型。生活润色仍保留，不以省略文案降低用户内容。
- 记忆整理只由聊天页手动触发，已有末条序号去重，无逐消息自动总结。保留手动操作语义。
- 批次逐子任务验证/存储，保留发送者、时间、会话及消息气泡；缺失结果仅重试该子任务。未改变原部分结果恢复机制。

## 主要剩余瓶颈

严格知识隔离和因果依赖限制聊天合批机会；重大事件/演化/报告等任务不适合无条件合并。批次JSON仍有ID封装开销，已有聊天紧凑协议主要服务单任务。不同快照和输出预算会分裂批次。旧非计划线下路径仍需阶段规划请求。实际缓存命中、费用和人物语言表现需要将来的受控真实对照，本轮未付费测试。
