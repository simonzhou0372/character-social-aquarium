# Character Social Aquarium — 第二轮功能更新与模拟系统优化

## 一、任务说明

当前项目已经完成第一版 Demo。请在现有工程基础上继续迭代，完成以下九项更新。

本轮工作的核心目标：

1. 补充角色与用户的基础资料能力。
2. 让虚拟世界时间可直接控制，并支持任意虚构纪年。
3. 增加与线上聊天并行的现实场景互动系统。
4. 显著提升角色自主社交的活跃度。
5. 引入只作为世界背景存在的名人、传闻人物与团体。
6. 提高生活时间轴的信息密度与可读性。
7. 完善 API 预算控制。

这是在已有 Demo 基础上的增量开发。

必须尽量复用现有角色、关系、世界、模拟器、聊天、知识库及 UI 组件，不能无故重建项目、清空存档或破坏原有功能。

# 二、更新一：角色性别设置

在角色创建和角色编辑界面中，增加字段：

**性别（Gender）**

要求：

- 使用普通文本输入框。
- 不采用只能选择男女的下拉框。
- 不设置性别枚举限制。
- 可以填写男性、女性、无性别、非二元、自定义身份或任何虚构作品中的性别概念。
- 允许留空。
- 默认不通过 AI 推断。
- 角色资料 AI 帮写可以提供建议，但不能未经用户确认自动覆盖。
- 用户填写后，自动加入相关 AI 上下文。
- 不需要在每次聊天前单独调用 AI 判断性别。

建议存储为：

`gender?: string`

该字段必须包含在角色导入导出、资料展示及编辑功能中。

如果为空，AI 仅根据其他已知设定自然表达，不得强制猜测或自动持久化。

# 三、更新二：世界运行速度与暂停快捷控制

## 3.1 必须成为全局醒目控件

在 PC 和手机端，用户都应该能直接看到：

- 当前世界是否运行。
- 当前模拟速度。
- 暂停 / 继续按钮。
- 速度调整入口。
- 当前世界日期与时间。

这些操作必须位于主界面一级交互区域。

不允许要求用户进入设置页面才能调整。

### PC 端

建议在顶部状态栏设置一个具有游戏 HUD 风格的时间控制区。

示例：

`W1 · AD 2026/10/22  18:30     ?  1×  [速度]`

暂停后，播放按钮变成继续按钮，并明确显示“已暂停”。

### 手机端

在顶部或始终可见的紧凑状态栏中提供：

- 世界时间。
- 暂停 / 继续。
- 当前倍率。

点击倍率后弹出快捷速度菜单。

不得因小屏幕隐藏核心控制功能。

## 3.2 速度档位

按现有的即可。

速度切换必须立即生效。

## 3.3 暂停规则

暂停后：

- 虚拟世界时钟停止。
- 不继续生成新的生活事件。
- 不继续触发自主聊天。
- 不生成新的线下互动。
- 不自动推进角色生活状态。
- 已保存数据仍可正常查看。
- 用户仍可编辑角色、世界和设置。

暂停前已经开始的 AI 任务不能在恢复前悄悄推进世界。应安全完成、暂存或取消，并由统一任务控制器处理。

**重要：暂停不能被离线时间补全绕过。**

如果用户暂停后关闭浏览器，第二天重新打开，世界仍应暂停，不得把这一天自动补全。

## 3.4 模拟速度与现实时间的关系

1× 表示现实一分钟对应虚拟世界一分钟。

5× 表示现实一分钟对应虚拟世界五分钟。

时间推进速度与 AI 请求频率不是同一个概念。

请使用统一模拟时钟驱动事件调度，而不是通过加速发送请求来伪装时间加速。

例如一个角色还有两小时下班：

- 1×：虚拟时间两小时后下班。
- 10×：现实约十二分钟后下班。

在高倍速下应采取事件批处理及合理的内容密度控制，防止大量 API 请求同时爆发。

## 3.5 多世界独立控制

每个世界应保存自己的：

- 当前虚拟时间。
- 运行速度。
- 暂停状态。
- 最后模拟检查点。

切换世界后，全局控制条显示当前世界对应状态。

不得将 A 世界的时间倍率错误应用到 B 世界。

若一个角色同时属于多个世界，必须保证不同世界中的模拟状态互不污染。

# 四、更新三：现实场景中的多人互动

这是本次最重要的新增功能之一。

现有产品已经能够生成线上私聊与群聊，但角色在现实场景中共同活动时，也应产生可以独立观察的**线下对话记录**。

需要新增：

**现实互动 / 线下观察（In-Person Interactions）**

这是与线上聊天并列的核心功能，不是把普通聊天室换一个标题。

## 4.1 现实互动的基本概念

当多个角色在同一地点参与共同活动时，可能触发线下互动。

例如：

- 一起上学。
- 放学同行。
- 排练。
- 一起吃饭。
- 购物。
- 家庭聚会。
- 约会。
- 社团活动。
- 工作会议。
- 偶遇。
- 一起旅行。

角色可以边进行活动边交谈。

线下聊天需要考虑：

- 所在地点。
- 场景氛围。
- 当前共同活动。
- 参与成员。
- 人物距离及相互关系。
- 角色正在做什么。
- 有谁中途离开或加入。
- 场景的开始、发展与结束。

## 4.2 线下互动与网上聊天的区别

线下互动不能直接复用网聊的短消息生成规则。

两种形式分别具有不同特点。

### 网上聊天

- 相对零碎。
- 回复不一定及时。
- 可能已读不回。
- 存在较长时间间隔。
- 消息较短。
- 角色可以同时进行其他活动。

### 现实互动

- 同一个场景中可以持续多轮对话。
- 多人发言更加连续。
- 交谈密度明显高于网聊。
- 允许插话、打断、争论。
- 允许共同动作影响谈话。
- 存在短暂沉默。
- 参与者可以进入或离开场景。
- 场景可以细分为多个活动阶段。

例如：

两位角色去咖啡店。

首先进入咖啡店并找座位。

随后点餐。

等待期间闲聊。

饮品端上来后继续交流。

最后结账并离开。

这不应该只被压缩成一条“二人去咖啡店”的时间轴记录。

## 4.3 线下互动观察界面

新增一个独立入口：

**线下观察**

在 PC 与手机端均应方便进入。

界面与线上聊天保持同一产品的整体设计语言，但采用更适合阅读场景记录的样式。

建议结构：

- 顶部显示场景标题、地点、日期、参与角色。
- 中间为按时间排列的对话及活动记录。
- 不同角色使用不同的头像、姓名和强调色。
- 活动阶段使用独立的视觉分隔。
- 重要动作与环境变化使用场景说明卡片。
- 用户可展开详细事件信息。

示例：

【咖啡店 · 下午 15:20】

【阶段：入店】

祥子：今天这里倒是挺安静的。

初华：因为还没到晚餐时间吧。

【15:26 · 两人找到靠窗的位置】

【阶段：点餐】

初华：祥子想喝什么？

祥子：红茶就好。

【15:34 · 店员送上饮品】

【阶段：休息闲聊】

……

上述仅为展示结构的示例，正式数据必须由真实的场景事件与 AI 生成结果驱动。

对话、活动阶段和旁白说明应具有清晰的视觉区别。

不要将全部内容渲染成普通聊天气泡。

## 4.4 场景分阶段

每个线下事件允许拆分为多个阶段。

建议数据结构：

- Scene ID
- World ID
- Location
- Participants
- Start Time
- End Time
- Scene Phases
- Dialogue Entries
- Activity Entries
- Related Events

每个阶段包含：

- 开始与结束时间。
- 当前参与成员。
- 活动内容。
- 具体对话。
- 环境或行为变化。
- 阶段小结（可选）。

支持点击阶段跳转阅读。

## 4.5 线下对话密度

线下互动中的对话应明显多于同一时长的线上聊天。

但是：

**不能把每一分钟都强行填满对白。**

请根据场景重要性决定内容量。

例如：

- 普通短暂偶遇：几句交流即可。
- 一起吃午饭：可以出现多轮自然聊天。
- 长时间排练：更多体现活动阶段，穿插部分对话。
- 双人约会：可以具有较丰富的连续互动。
- 多人聚会：能够自然呈现多人交谈和不同话题。

对话生成应具有自动分批、分阶段和成本限制。

可以在内部以结构化批次生成连续对白，但不允许失去时间与角色一致性。

## 4.6 历史归档与筛选

所有线下场景都需要保存。

用户可以按照以下维度筛选：

- 世界观。
- 日期或时间范围。
- 单个角色。
- 多个角色的共同参与。
- 团体。
- 地点。
- 场景类型。

对于多角色筛选，请支持：

- 包含任意选中角色。
- 必须同时包含所有选中角色。

尤其需要便于用户追踪一组 CP 的共同活动历史。

按时间倒序展示历史场景卡片。

点击可以完整阅读，不因离线补全或记忆总结而直接删除原始记录。

## 4.7 与原系统的联动

线下场景必须与原有生活模拟系统耦合。

- 同一个共同活动只能建立一个事实上的主事件。
- 时间轴可以显示该事件。
- 点击时间轴事件可以进入线下观察详情。
- 相关角色的记忆可以引用该事件。
- 之后的线上聊天可以自然提及该事件。
- 不在场、未被告知的角色不能凭空知道具体对话。

用户离线期间发生的线下场景也可以补全。

离线时间跨度很长时，不要求完整生成全部普通生活场景，应优先生成具有社交价值的片段。

## 4.8 单独配置线下生成提示词

在现有“设置 → AI 设置 → 提示词管理”中，增加：

**线下互动生成（In-Person Scene Generation）**

默认提示词：

你正在为一个持续运行的虚拟角色世界生成现实场景中的人物互动。

- 根据角色性格、关系、共同活动、地点与时间生成自然对话。
- 线下对话可以比网上聊天更连续、更密集。
- 允许角色插话、打断、沉默、转移注意力。
- 对话需要随着场景中的活动自然变化。
- 角色可以进行符合情境的小动作，但避免夸张、重复的动作描写。
- 不能把人物对话写成冗长小说。
- 不要频繁插入文学化旁白。
- 不要每一句对话后面都加人物动作。
- 避免角色像 AI 客服一样回答问题。
- 不要让每个场景都产生重大剧情事件。
- 人物称呼和说话习惯必须符合关系设定。
- 不允许角色知道自己未曾接触的信息。
- 输出应能被程序解析为明确的场景阶段、对话条目和活动条目。

注意：

聊天不显示 Markdown 的规则继续适用，但结构化内部响应可以使用 JSON。

线下对话不应被线上聊天的 1～3 条短消息规则机械限制。

# 五、更新四：自定义世界纪年与初始日期

## 5.1 世界观纪年

在世界创建和编辑界面新增：

**纪年名称**

默认值：

`AD`

允许任意自定义文本。

例如：

- AD
- CE
- 帝国历
- 星历
- 新历
- 魔法纪元
- 自定义作品历法名称

纪年必须加入世界基础设定。

例如：

世界使用“帝国历”，当前日期为“帝国历 325 年 4 月 12 日”。

AI 应理解这是世界内部的纪年，而不是自动转换成现实公元日期。

## 5.2 世界初始日期

创建世界时必须提供：

**故事从哪一天开始？**

允许用户手动设置：

- 年
- 月
- 日
- 时
- 分

默认可以使用当前现实日期，纪年为 AD。

但用户必须能够自由修改。

例如：

- AD 30 年。
- AD 2026 年。
- AD 23456 年。
- 帝国历 325 年。
- 星历 1 年。

不允许限制为四位数年份。

必须支持至少 1～999999 的年份范围，并正确处理两位数、五位数和六位数年份。

## 5.3 禁止依赖原生日期控件处理虚拟世界日期

不能把浏览器原生 `input type="date"`、系统日期选择器或 JavaScript Date 字符串解析作为虚拟世界日期的唯一实现。

不能通过调用 AI 或外部 API 处理简单日期输入。

应实现自己的年月日时分选择组件。

年份使用自由输入的数字框。

月份、日期、小时和分钟可采用适当的选择器。

必须提供：

- 输入校验。
- 闰年计算。
- 每月天数校验。
- 日期递增。
- 跨年计算。
- 大年份支持。
- 格式化显示。
- 保存与恢复。

建议单独实现 WorldCalendar / WorldDateTime 数据结构。

虚拟日期计算可以采用可验证的整数日序号与日内时间偏移方案。

不要依赖有范围和解析歧义的浏览器日期 API。

## 5.4 纪年与历法的区别

第一版只要求：

- 允许自定义纪年名称。
- 允许自定义纪年年份。
- 默认采用公历式的 12 个月、闰年和日期规则进行运算。

不需要立即实现完全自定义的星球历法、特殊月份数量或特殊闰年规则。

但需要预留 calendarSystem 字段，以便未来扩展。

## 5.5 初始时间与运行时间

必须区分：

**世界故事开始时间：** 用户创建世界时指定的第一天。

**当前世界模拟时间：** 经过模拟后推进到的日期。

世界创建后从用户设定的初始日期开始运行。

不可因为故事年份是 23456 年，就认为需要补全现实中的数万年。

离线补全只计算实际上次运行后经过的现实时间，再结合模拟倍率推进世界时间。

如果修改已存在世界的纪年显示名称，不应自动重置世界进度。

如果修改已存在世界的初始日期或当前模拟时间，必须提示可能影响历史事件顺序，提供安全的修改或迁移方案。

# 六、更新五：大幅提高自主聊天频率

目前 Demo 的“热闹”模式仍然明显偏冷清。

请重新设计活跃度档位。

**当前版本的“热闹”模式活跃程度，应当调整为新版本的“安静”模式基准。**

在其基础上新增明显更活跃的“标准”和“热闹”。

## 6.1 三档预期

### 安静

接近旧版热闹模式。

- 社交活动较少。
- 偶尔出现私聊。
- 群聊可以长时间安静。
- 以普通日常为主。

### 标准

活跃程度明显高于安静。

- 多个角色每天都有合理机会主动聊天。
- 关系亲密的角色更频繁联系。
- 活跃群聊可以出现持续讨论。
- 某些生活事件之后产生自然的聊天。
- 有人主动发起新话题。

### 热闹

明显高于标准。

- 角色之间经常产生交流。
- 群聊和私聊都更加活跃。
- 多个聊天可能在同一时段交替发生。
- 角色更倾向分享生活中的事情。
- 有更多自发互动和接续话题。
- 共同事件更容易形成后续社交。

但仍需符合睡眠、忙碌、性格与关系约束。

## 6.2 必须真正修改调度器

不能仅修改 UI 文案或提示词。

请实际检查：

- 定时扫描间隔。
- 社交机会产生率。
- 主动私聊概率。
- 群聊发起概率。
- 接续回复概率。
- 话题自然结束概率。
- 忙碌抑制系数。
- 冷却时间。
- 角色关系对主动性的影响。
- AI 调用预算是否限制了消息生成。
- 是否存在无意的全局并发瓶颈。

以上参数应通过集中配置管理，并实际连接模拟引擎。

推荐使用基于**模拟时间**的机会产生率，而不是简单使用现实时间固定间隔。

对于同等数量、相同设定的角色：

热闹模式应当可统计地比标准模式产生更多互动，标准模式明显高于安静模式。

## 6.3 建议校准方法

建立固定随机种子、固定人物关系和固定日程的测试世界。

分别运行三个档位的模拟时间 24 小时。

统计：

- 主动发起聊天次数。
- 回复消息数量。
- 群聊活跃会话数。
- 私聊活跃会话数。
- 参与社交的角色比例。
- 平均消息间隔。
- API 请求数量。

可采用如下初始目标进行调优：

| 档位 | 相对旧版热闹的目标社交事件量 |
|---|---|
| 安静 | 约 1× |
| 标准 | 约 3× |
| 热闹 | 约 6× |

这些倍数是初始校准目标，不是每个角色必须发送固定数量消息的硬性指标。

请以多次模拟统计确认差异。

如果 API 预算不足，应明确显示“受到用量限制”，而不是让用户误以为热闹模式本来就这么冷清。

## 6.4 性能与成本控制

提高活跃度不等于对每个角色反复单独发送 API 请求。

应优先：

- 批量生成连续消息。
- 合并相关社交事件。
- 复用已加载的上下文。
- 设置合理并发上限。
- 避免重复读取大量不相关记忆。

角色在线下共同活动期间，也应相应减少不合理的线上即时聊天。

# 七、更新六：传闻人物、名人及传闻团体

现有系统主要管理能够参与模拟的角色和团体。

需要加入另一种实体：

**背景实体（Background Entities）**

允许它们存在于世界设定与人物认知中，但不参与日常自动模拟。

## 7.1 背景人物

角色创建时新增模式：

- 可互动角色
- 背景人物 / 传闻人物

背景人物可包含：

- 名称
- 头像（可选）
- 性别（自由文本）
- 简介
- 所在世界
- 名气程度
- 身份及社会角色
- 相关传闻
- 已确认事实
- 哪些角色认识或听说过此人

例如：

某个世界中存在著名音乐家 X。

部分人物知道 X，可能在闲聊中讨论他的演出。

但是 X 本人不会自动出现在聊天列表中，不会自主生活，也不会主动加入活动。

## 7.2 背景团体

团体同样增加：

- 可互动团体
- 背景团体 / 传闻团体

例如：

- 著名乐队。
- 某个企业。
- 神秘组织。
- 某个学校的知名社团。
- 传说中的冒险小队。

这些团体可以成为讨论对象，但不自动生成群聊和团体日程。

## 7.3 认知范围

最重要的是：

**并不是所有角色都天然知道某个名人或传闻。**

允许配置：

- 完全不知道。
- 听过名字。
- 了解部分信息。
- 比较熟悉。
- 亲自认识。

应允许为每个角色维护对背景人物或背景团体的认知关系。

名气程度可以影响角色听说该对象的概率，但不能代替明确的知识权限。

## 7.4 传闻可信度

需要区分：

- 已确认事实。
- 未证实传闻。
- 错误传闻。
- 角色个人看法。

AI 应根据角色实际掌握的信息进行表达。

例如角色听说某明星退团，但这只是谣言，就不能让所有角色立即将其认定为事实。

传闻可以通过正常互动传播，但需要记录来源和知情范围。

## 7.5 后续转为可互动角色

用户可以随时将背景人物升级为可互动角色。

升级时：

- 保留原实体 ID。
- 保留已有世界关系。
- 保留认知记录。
- 保留背景知识。
- 增加生活模拟配置。

不能因为升级而产生两个同名、互不关联的实体。

背景团体转为可互动团体时同理。

## 7.6 模拟器约束

背景实体：

- 不进入主动聊天候选池。
- 不消耗日常模拟调度资源。
- 不生成虚拟消息。
- 不自动参与线下活动。
- 不生成个人生活时间轴。

但可以被其他角色提及。

后续如果用户显式启用其互动能力，才开始参与模拟。

# 八、更新七：生活时间轴去噪

当前时间轴充满睡觉、休息等意义较低的普通生活信息，影响真正值得观察的事件。

需要改进展示策略。

## 8.1 核心原则

**不要删除底层生活状态，只改变观察层的展示重点。**

睡眠、休息、通勤等状态仍是模拟器正确运行的重要依据。

但它们不应该默认占据大量时间轴空间。

## 8.2 默认展示内容

优先显示：

- 多人共同活动。
- 有意义的社交事件。
- 特殊外出。
- 排练、演出、约会、聚会。
- 重要状态变化。
- 人物关系进展。
- 重要意外事件。
- 有关联线下对话的活动。
- 具有故事意义的单人事件。

默认隐藏或折叠：

- 普通睡眠。
- 普通休息。
- 常规起床。
- 常规吃饭。
- 无特殊情况的通勤。
- 没有重要互动的重复工作日程。
- 其他纯状态维持记录。

例如：

“祥子睡了七小时”不应占据一张显眼的事件卡片。

“祥子因为某件事情失眠，并在凌晨联系了初华”则值得保留。

## 8.3 时间轴筛选

增加：

- 精选事件（默认）
- 全部事件
- 社交互动
- 共同活动
- 重要个人事件
- 日常状态

允许用户自行显示或隐藏普通状态。

## 8.4 多事件合并

允许把连续、重复、意义较低的状态合并。

例如：

多次普通休息不必逐项列出。

长时间常规工作可以显示为紧凑背景区间，而不占据完整事件卡片。

多人共同参与一个活动时优先显示一条关联事件，避免为每个人生成重复卡片。

## 8.5 与线下观察联动

有详细线下对话的事件，应显示：

- 参与人物。
- 活动名称。
- 时间。
- 场景阶段数量。
- 查看线下对话入口。

点击后跳转到对应场景档案。

# 九、更新八：模型用量限制增加无限制选项

目前 API 模型用量设置允许配置限制值。

请增加：

**不限制模型用量**

采用明确的开关。

## 9.1 开关逻辑

关闭：

正常应用用户设置的 Token、请求次数或金额限制。

开启：

取消应用内部的模型用量硬限制。

但仍需遵守：

- API 提供商的真实额度限制。
- API 请求并发约束。
- 提供商限流。
- 网络错误重试上限。
- 防止无限循环的程序保护。

**不限制用量不意味着无限并发或无限重试。**

## 9.2 界面要求

启用时显示清晰说明：

“不限制应用内部的模型请求和 Token 总预算，可能产生较高 API 费用。服务商自身限额仍然有效。”

用户应能看到：

- 已消耗 Token。
- API 请求次数。
- 如有可信模型定价，可显示估算费用。

关闭无限制选项后，之前设置的限额值应保留并恢复生效。

## 9.3 运行中调整

切换后应影响后续请求。

不能因为原本已经达到限制，导致开启无限制后仍无法正常模拟。

模型仍然出现额度错误时，应显示来自服务商的真实错误原因。

# 十、更新九：用户个人头像上传

现有角色头像功能应扩展至用户个人资料。

在用户身份设置中加入：

**上传头像**

支持：

- 本地文件选择。
- 拖拽上传（适用界面）。
- 头像裁剪。
- 预览。
- 更换。
- 恢复默认头像。

兼容常见图片格式。

需要进行文件类型、大小和图像解码校验。

头像保存到现有本地资源存储中。

应用于：

- 用户资料卡。
- 用户发送的聊天消息。
- 用户参与的群聊。
- 用户个人身份选择界面。
- 相关角色扮演入口。

注意区分：

用户以自己身份发送消息时，使用用户自己的头像。

用户扮演某个角色时，使用被扮演角色的头像。

不能因为切换身份导致历史消息头像及发送者信息混乱。

用户头像应被正常包含在数据导出与导入流程中。

# 十一、全局架构一致性要求

本次增加了线下观察、纪年、背景实体和更快的模拟速度，需要检查原有模块之间的数据耦合。

## 11.1 时间系统

所有模拟事件使用统一的虚拟时间表示。

不得：

- 线上聊天使用现实时间，线下场景却使用虚拟时间。
- 大年份导致日期解析失败。
- 切换纪年后历史顺序变化。
- 世界暂停后仍持续产生新事件。
- 高速模拟导致定时任务重叠。
- 离线补全忽略世界之前的运行倍率或暂停状态。

请明确设计现实时间与模拟时间之间的映射及检查点策略。

修改倍率或暂停时，应保存时间控制状态及对应的时间锚点，确保离线恢复能够正确计算。

## 11.2 活动与对话的统一事实来源

网上聊天、线下互动、时间轴与记忆系统必须引用统一的生活事件。

例如：

A 和 B 下午一起去咖啡店。

这个事实应同时能够被：

- 时间轴展示。
- 线下观察打开。
- A 和 B 的相关记忆引用。
- 后续线上聊天提及。

不应分别生成四个内容不一致的版本。

## 11.3 提示词系统集成

新的线下场景提示词必须集成至现有全局提示词管理器。

增加提示词时：

- 支持用户编辑。
- 支持恢复默认。
- 支持持久化。
- 支持导入导出。
- 不覆盖已有自定义提示词。
- 不破坏原本的内部 JSON 结构化输出。

## 11.4 数据迁移

已有存档必须安全兼容。

旧角色：

性别默认为空。

旧世界：

纪年默认为 AD。

旧世界初始时间：

依据已有可靠模拟时间及记录进行兼容迁移，不得擅自重置。

旧团体和角色：

默认作为可互动实体。

旧 API 设置：

默认保留原有限额模式。

旧消息、世界关系和角色头像：

不得丢失。

请增加数据版本迁移与回归测试。

# 十二、验收测试

必须针对本轮更新建立或扩展测试。

### A. 性别字段

测试中文、英文、任意文本、空值的保存与上下文使用。

### B. 世界速度

测试暂停、继续，确认虚拟时间准确推进。

测试暂停后关闭浏览器再打开，不进行错误补全。

测试不同世界的时间状态独立。

### C. 线下场景

创建两人共同活动，确认能生成：

- 场景。
- 多个阶段。
- 对话。
- 活动说明。
- 时间轴关联。
- 角色记忆引用。

多人场景不得产生错误发言人 ID、重复活动和不合理的同时出现。

### D. 历史筛选

按单人、多人同时参与、世界、日期范围筛选线下观察历史，验证结果正确。

### E. 虚拟纪年

测试：

- AD 30 年。
- AD 2026 年。
- AD 23456 年。
- 帝国历 325 年。
- 星历 999999 年。

验证创建、编辑、跨月、跨年、闰年、保存和恢复。

不得出现年份被自动变成 1930、2030 或其他错误情况。

### F. 活跃度

用固定随机种子和相同测试世界比较三档配置。

确认：

新热闹明显高于新标准，新标准明显高于新安静。

新安静大致相当于旧热闹的活跃程度。

### G. 背景实体

创建一位传闻人物及一个背景团体。

它们可以被知道其存在的角色提及。

但不会进入模拟活跃角色池。

将背景人物升级为可互动角色后，原有知识与关系仍然存在。

### H. 时间轴

普通睡眠、休息等事件在精选模式中不应泛滥。

切换全部事件后仍可看到原始状态记录。

### I. 无限制 API

启用后不再触发应用内部 Token 总预算拦截。

关闭后恢复既有限制值。

提供商 429、额度不足等错误仍能正确处理。

### J. 用户头像

上传后正确显示、刷新后保留、导出导入后可恢复。

切换角色扮演身份不会错误覆盖头像。

# 十三、实施要求

请按以下顺序推进：

1. 检查现有项目的数据模型和模拟引擎。
2. 完成世界时间、纪年及暂停速度控制。
3. 完成线下活动阶段和对话的数据结构。
4. 实现线下观察界面及归档筛选。
5. 重构并校准三档活跃度。
6. 加入背景人物和背景团体。
7. 优化时间轴精选规则。
8. 补齐性别、用户头像、无限制 API 选项。
9. 完成数据迁移、移动端检查及自动化测试。

此顺序是建议的工程依赖顺序，不是要求每一步都独立交付。

请直接修改现有项目代码，不要只输出设计方案。

在可用的开发环境中实际执行构建、测试和浏览器验证。

如果项目已经实现某部分功能，应复用和改进，而不是重复创建第二套系统。

不要因为新增线下互动而牺牲原本的线上聊天体验。

**最终目标：让角色既有足够活跃的线上社交，也有连续、可回顾、细节丰富的线下共同生活，同时让用户能像控制一款模拟游戏一样直观控制整个世界的时间。**


有一点在实现时尤其重要：线下观察的内容生成频率应独立于网上聊天频率。否则把整体活跃度提高到 6 倍后，线下场景可能产生过量对白和 API 消耗。最合理的方案是提高线下事件的发生机会，再根据事件的重要性分配对白生成预算，而不是所有事件都生成同等长度的对话。
