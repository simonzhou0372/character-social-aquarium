# Character Social Aquarium — 第三轮增量开发需求：观察范围、静默模拟、角色演化与世界定期报告

## 一、开发目标

请在现有项目基础上新增三套相互关联的系统：

1. **选择性观察与静默模拟系统（Selective Observation）**
2. **世界观独立的人物动态演化系统（Character Evolution）**
3. **世界定期报告系统（World Periodic Reports）**

本次更新的主要目标是解决大型世界观中角色数量过多导致的 AI Token 浪费、聊天与事件信息爆炸，以及长期模拟缺乏重点的问题。

核心理念：

**用户不是必须观察整个世界，而是可以把注意力集中在自己关心的人物、CP 和团体上。未被观察的世界仍然存在，但不需要被完整模拟和记录。**

请直接修改当前项目并完成必要的数据迁移、测试与界面集成。不要重新构建已经存在的聊天、生活模拟或世界观管理模块。

# 二、选择性观察系统

## 2.1 基础设计

为每个世界观增加独立的“观察范围”设置。

用户可以自由选择：

- 需要观察的角色。
- 需要观察的团体。
- 需要观察的双人关系 / CP。
- 是否观察整个世界。

建议提供以下观察模式：

**全量观察**

保持现有运行方式，所有可互动实体均可正常生成生活事件与社交消息。

**选择性观察**

只有被用户指定的角色、团体及关系进入完整模拟范围。

其他实体进入静默状态。

选择性观察是大型世界观推荐使用的默认模式，但已有存档升级后应保留原有行为，不能未经用户同意将现有角色全部静默。

## 2.2 观察范围的具体规则

观察对象可以相互重叠，但不能因此产生重复模拟。

例如：

用户选择观察角色 A，同时选择团体 G。

A 本身也是 G 的成员。

A 只能拥有一份生活状态、一条统一的事件历史，不能被两个独立模拟器重复驱动。

不同观察维度应采用以下逻辑：

### 观察单个角色

完整观察该角色的：

- 日常生活中的重要事件。
- 线上私聊。
- 参与的群聊。
- 线下共同活动。
- 人际关系互动。
- 重要个人经历。

如果该角色与静默角色产生互动，允许临时生成静默角色参与的必要对话。

但不能因此让静默角色的全部其他社交活动自动激活。

### 观察团体

重点观察：

- 团体内部的共同活动。
- 团体群聊。
- 团体有关的重要事件。
- 团体成员因团体事务产生的互动。

不能仅仅因为某个角色属于被观察团体，就自动完整模拟其所有私人社交网络。

### 观察双人关系

重点观察指定双方的：

- 私聊。
- 共同活动。
- 关系发展。
- 与双方关系直接相关的重要事件。

第三方可以在需要时参与相关场景，但不会因此自动进入完整观察范围。

### 全量观察

保留当前原有模拟行为。

## 2.3 静默实体（Dormant Entities）

未被观察的角色和团体进入静默状态。

静默不是删除、死亡、消失，也不是永久冻结人物时间。

而是：

**暂停细粒度的生活、聊天和社交内容生成，仅维持必要的宏观背景状态。**

静默状态下：

- 不定期生成普通私聊。
- 不自动生成普通群聊。
- 不生成完整线下对白。
- 不记录睡觉、吃饭等日常流水账。
- 不持续调用 AI 更新性格和记忆。
- 不频繁参与普通生活事件的随机抽样。
- 不为每个静默人物维护高频调度任务。

但是仍保留：

- 世界中的身份及存在。
- 团体成员关系。
- 与观察角色的人际联系。
- 重要的已知事实。
- 必要的宏观生活背景。
- 特殊事件的潜在参与资格。

静默实体不应消耗与活跃实体相近的模拟资源。

## 2.4 静默角色对观察世界的影响

静默人物仍有可能影响被观察者。

例如：

A 是被观察角色。

B 是未被观察角色。

B 与 A 在同一个学校，但用户并不关心 B 的个人日常。

正常情况下，不需要模拟 B 的全部生活。

但以下事件可以发生：

- B 突然转学，影响 A 的学校生活。
- B 在某个重要活动中与 A 发生冲突。
- B 向 A 透露重要消息。
- B 与 A 的共同朋友发生重大事件。
- B 所属团体发生变动，影响 A 的工作或活动安排。

此时才需要激活涉及 B 的必要事件生成。

事件完成后，B 可以重新返回静默状态。

**静默角色不能只要与观察角色有一条关系，就源源不断地产生事件。**

建议采用关系强度、事件影响程度、事件类型与概率阈值决定是否生成。

大型世界应优先使用低频、群体级别的宏观事件抽样，而不是轮询每一个静默人物。

## 2.5 防止社交网络级联激活

这是必须防范的问题。

假设：

- 用户观察 A。
- A 认识 B。
- B 认识 C。
- C 认识 D。

不能因为 A 认识 B，就激活 B 的全部社交关系，进而激活 C、D，最后整个世界再次进入完整模拟。

完整模拟范围只由用户指定的观察配置决定。

其他人物只能作为相关事件的临时参与者。

不要递归扩张观察范围。

# 三、从静默切换到观察：自动补全前三天

## 3.1 强制回溯机制

当一个角色、团体或双人关系从未观察状态切换为观察状态时，自动启动历史补全。

**默认至少补全当前世界模拟时间之前的三个完整虚拟日，即向前覆盖至少 72 小时。**

例如：

当前世界时间为：

AD 2026 年 10 月 22 日 18:00。

用户开始观察角色 A。

应尝试补全 A 从 10 月 19 日 18:00 到 10 月 22 日 18:00 之间值得记录的生活与互动。

注意：

- 使用虚拟世界时间，不是现实时间。
- 不受当前模拟倍率影响回溯长度。
- 如果世界创建至今不足三天，仅回溯到世界开始时间。
- 世界采用特殊纪年或大年份时仍然正常运算。
- 如果已有该时间段的部分记录，只补充缺失内容。
- 不得重复已经存在的消息或事件。

## 3.2 回溯对象

角色被观察：

补全该角色的近期生活、重要活动和有意义的聊天。

团体被观察：

补全该团体近期的共同活动和相关群聊。

双人关系被观察：

补全双方最近三天的私聊、共同活动以及重要关系事件。

对于多个对象同时被激活的情况，应合并重叠的补全任务，避免重复生成同一个共同事件。

## 3.3 回溯内容生成原则

不要求补全每一分钟，也不要求三天内所有人物都有大量对话。

回溯应覆盖三天的时间范围，生成合理的代表性内容。

例如：

- 一次共同外出。
- 若干重要聊天。
- 一次群体活动。
- 相关生活事件。
- 必要的历史背景摘要。

安静性格的人可能三天内没有很多互动，不应被强制灌入无意义消息。

## 3.4 历史一致性

必须处理已经存在的历史事实。

例如：

A 原本处于静默状态。

但此前 A 曾参与被观察角色 B 的线下活动。

现在用户开始观察 A。

回溯生成的内容不能与那次活动矛盾。

禁止：

- 同一时间出现在两个互斥地点。
- 已存在的聊天再次生成。
- 新补全事件推翻已确认历史。
- 将当前时间之后才获得的信息写入三天前的对话。
- 让回溯内容无理由改变过去已经确定的关系发展。

建议回溯前查询已有事件、消息及日程，并建立时间占用约束。

可以记录：

- `occurredAt`：事件在世界中发生的时间。
- `generatedAt`：内容实际被补全生成的时间。
- `origin`：实时模拟或历史回溯。

如果历史约束无法允许生成新的事件，应保留已有事实，以摘要形式补齐其余内容，而不是强行插入矛盾的剧情。

## 3.5 补全交互

自动显示与现有离线补全风格一致的游戏化加载界面。

例如：

- “正在打听这位角色最近的生活……”
- “正在回收过去三天的聊天记录……”
- “正在调查这两个人有没有偷偷见面……”
- “正在整理社团最近发生的事情……”
- “正在检查缺失的不在场证明……”

显示：

- 回溯时间范围。
- 已完成的日期。
- 已补全事件数。
- 已补全消息数。
- 任务进度。
- 取消及继续选项。

补全应采用分批生成和持久化检查点。

当用户一次激活大量人物时，不应同时发起大量 API 请求。

如果因 API 限额、网络异常或用户取消而不能完成三天的覆盖，应将该观察对象标记为“历史补全未完成”，保留剩余任务，后续继续。

不能将只完成了一小段内容的回溯显示为已完成。

## 3.6 重新取消观察

当用户取消观察某个角色或团体时：

- 不删除已有历史。
- 停止后续细粒度模拟。
- 保留关键状态。
- 返回静默模式。

再次观察时，只补全实际缺失的区间。

已经存在的完整历史不得重复生成。

# 四、观察范围的 UI

新增“世界设置 → 观察管理”。

提供：

- 全量 / 选择性观察切换。
- 角色搜索。
- 团体搜索。
- 双人关系选择。
- 批量勾选。
- 已观察 / 静默筛选。
- 观察范围预览。
- 一键观察整个团体。
- 一键取消不必要的观察。
- 对新观察对象启动历史补全。

角色及团体卡片应显示明确状态：

- 正在观察。
- 静默。
- 历史补全中。

这些状态不应采用过于复杂的多层设置。

在世界首页显示简洁统计：

例如：

正在观察：8 名角色、2 个团体。

静默：43 名角色、6 个团体。

必要时显示当前观察范围带来的模拟负载。

PC 和手机端都应容易修改观察目标。

# 五、世界观独立的角色动态演化系统

## 5.1 世界级配置

在“创建 / 编辑世界观”中新增：

**允许人物设定随经历自然变化**

默认建议关闭，以保留已有角色设定的稳定性。

用户可为每个世界单独开启或关闭。

例如：

- 原作还原世界：关闭。
- 长期生活模拟世界：开启。
- 校园 AU：开启。
- 剧情演绎世界：根据用户选择。

不得将一个世界的配置直接应用到所有世界。

## 5.2 关闭时的规则

关闭自动演化后：

- 角色基础性格保持稳定。
- 已锁定的说话习惯保持稳定。
- 人物身份和基础设定不被 AI 自动永久修改。
- AI 不自动重写角色档案。
- 长期模拟不能无理由将角色变成完全不同的人。

但角色仍然可以：

- 短暂高兴。
- 生气。
- 沮丧。
- 产生临时情绪变化。
- 在具体事件中改变当下态度。
- 形成对事件的记忆。
- 按已有规则发展可变的人际关系。

**禁止自动演化不等于角色成为没有情绪变化的机器人。**

## 5.3 开启时的规则

开启后，角色可以在长期经历影响下缓慢发生合理变化。

例如：

- 原本孤僻的人逐渐愿意主动交流。
- 某次失败使角色暂时失去自信。
- 长期合作让人物形成新的行为习惯。
- 经历重大事件后改变某些价值判断。
- 长期生活环境变化使角色调整日常习惯。
- 某段重要关系影响人物对亲密关系的态度。

这些变化必须有具体原因。

不能因为模型随机生成一句话，就直接永久改变角色性格。

## 5.4 演化层级

建议区分：

**临时状态**

心情、疲劳、短期兴趣等。

可以较频繁变化。

**长期倾向**

社交主动性、信任倾向、习惯、部分价值判断等。

需要多个相关事件支持，或有足够重要的明确事件作为依据。

**核心身份设定**

角色姓名、原作身份、基础背景、用户锁定的人物特征等。

默认不允许自动修改。

即使开启动态演化，也不代表 AI 拥有无限制重写人设的权力。

## 5.5 设定锁定与可演化字段

请为角色设定引入可锁定机制。

例如：

- 固定设定。
- 允许自然演化。

世界级开关是总控制。

角色级锁定是进一步限制。

用户明确锁定的属性不能自动改变。

已存在的世界覆盖设定优先于原始角色基础设定。

角色 A 同时存在于两个世界：

在 W1 中经历事件并变得更加开朗，不应导致 W2 中的 A 也自动发生同样变化。

必须将长期演化结果保存在对应的世界上下文内，而不是无条件修改全局 Character 基础资料。

## 5.6 演化触发

不要每经过固定几分钟就调用 AI 判断角色有没有变。

应采用事件驱动机制。

可能触发评估的情况：

- 重大个人事件。
- 长期重复的生活经历。
- 重要关系进展。
- 多次同类型情绪或行为变化。
- 阶段性的长期记忆整理。

普通聊天不需要每次都进行人格变化评估。

优先由规则系统检测是否存在足够的变化依据，再低频调用 AI 提出可验证的演化建议。

演化结果应经过结构化校验、范围限制和锁定检查后才写入数据。

## 5.7 演化记录

增加“人物变化记录”。

至少保存：

- 角色。
- 所在世界。
- 变化时间。
- 变化字段。
- 变化前状态。
- 变化后状态。
- 触发事件。
- 变化原因。

用户可以查看角色为什么发生变化。

支持撤销单次演化。

撤销时应正确处理后续依赖，不允许简单覆盖导致历史状态不一致。

重大变化应在世界时间轴或定期报告中适度体现。

# 六、世界定期报告系统

## 6.1 功能概述

每个世界观可独立开启以下报告：

- 日报
- 周报
- 月报
- 季报
- 年报

五项分别使用独立开关。

用户可以只开启其中部分报告。

例如：

世界 A：日报、周报。

世界 B：月报、年报。

世界 C：全部关闭。

## 6.2 报告时间依据

所有报告按照**世界模拟时间**计算，而非现实系统时间。

支持自定义纪年和大年份。

周期定义：

- 日报：一个虚拟日结束。
- 周报：一个完整虚拟星期结束，默认周一为每周第一天。
- 月报：一个虚拟自然月结束。
- 季报：每三个虚拟自然月结束。
- 年报：一个虚拟自然年结束。

默认采用当前世界已有的公历式历法规则。

不能因为虚拟世界处于 AD 23456 年而出现日期计算错误。

暂停期间不生成新的报告。

高倍率模拟需要按实际跨越的虚拟周期正确归档。

## 6.3 报告内容

报告应根据周期长短调整详细程度，而不是简单将相同模板重复五次。

### 日报

重点呈现当天值得关注的内容：

- 重要事件。
- 主要共同活动。
- 有趣的线上交流。
- 值得回看的线下互动。
- 重要人物状态变化。

日报应简短，不必记录所有普通日常。

### 周报

重点总结本周：

- 人际互动趋势。
- 团体活动。
- 本周重要事件。
- 角色之间的新进展。
- 尚未解决的话题或约定。

### 月报

重点呈现：

- 主要故事线。
- 人物关系发展。
- 团体动态。
- 长期习惯变化。
- 重要事件对世界的影响。

### 季报

重点呈现：

- 本季度重大事件。
- 人物与团体整体变化。
- 持续发展的关系。
- 重要生活阶段。
- 可能延续到下一季度的事件。

### 年报

提供更有仪式感的年度回顾：

- 本年度重大事件。
- 主要角色的重要经历。
- 最值得回顾的共同活动。
- 具有代表性的聊天。
- 人物关系变化。
- 团体的发展。
- 重要的人物成长与设定演化。
- 本年度尚未解决的重要事情。

可以采用更丰富的游戏化视觉呈现。

但禁止为了让年报看起来精彩而捏造没有发生的事件。

## 6.4 报告范围与观察设置联动

报告默认聚焦当前用户正在观察的对象。

静默角色或团体不需要单独生成完整报告内容。

但是如果静默对象产生了足以影响观察对象的重要事件，应适当纳入报告。

例如：

用户观察的团体受到某个背景组织的重大影响。

即使背景组织没有被观察，该事件也应出现在相关报告中。

不能因为一个世界拥有 1000 个静默人物，就为所有人分别生成事件摘要。

## 6.5 报告生成机制

报告尽量基于已经保存的事实生成：

- 生活事件。
- 线上聊天。
- 线下场景。
- 关系变化。
- 人物演化记录。
- 已有中长期记忆摘要。

不得为了写日报额外生成一整天的随机生活。

推荐流程：

1. 模拟时钟进入新的报告周期。
2. 将刚结束的周期标记为待汇总。
3. 检索该周期已有重要事件。
4. 通过程序筛选、去重并统计。
5. 必要时调用 AI 生成自然语言报告。
6. 验证报告中的事实引用。
7. 保存报告。
8. 在报告中心展示。

报告必须引用已有事实，不能凭空编造新的历史。

## 6.6 避免报告 Token 爆炸

禁止每份报告都重新读取整个世界的全部历史。

应实现分层汇总：

- 周报可以参考已生成的日报与重要事件。
- 月报可以参考周报及关键原始事件。
- 季报可以参考月报。
- 年报可以参考季度及月度报告。

但不能只依赖上级摘要而彻底丢失重大原始事实。

如果日报没有开启，周报仍然应该能够直接根据事件生成。

不能要求用户必须开启日报才能生成周报。

### 高速与长时间离线

如果虚拟时间一次跨过大量报告周期，不能同时发起数百次 AI 请求。

需要：

- 报告生成队列。
- 去重机制。
- 任务状态保存。
- 批量处理。
- 历史报告按需生成。
- API 预算控制。

所有开启的报告周期应保留可查看、可补生成的归档记录；较久远的报告可以延迟到用户打开时生成。

如果某个周期没有值得总结的事件，可以生成简短的空闲报告，或使用无需 AI 的本地概况。

不应为了凑内容制造故事。

## 6.7 报告中心 UI

新增：

**世界报告 / World Reports**

支持：

- 按世界筛选。
- 按日报、周报、月报、季报、年报筛选。
- 按日期查找。
- 查看历史报告。
- 点击报告中的人物跳转资料。
- 点击事件跳转时间轴。
- 点击互动跳转线上或线下记录。

主界面可显示最新报告入口。

但不应频繁弹窗打断用户观察。

例如：

“本周观察报告已生成。”

报告生成完毕后提供适度提示即可。

对于未生成的历史报告，应提供生成按钮与任务状态。

## 6.8 报告独立提示词

在现有全局提示词管理器中增加：

**世界报告生成（World Report Generation）**

默认提示词：

你是一个虚拟世界的观察记录员。

请根据提供的真实事件、聊天记录、关系变化与人物记忆，生成对应时间范围的世界观察报告。

要求：

- 严格依据已提供的事实。
- 不得捏造未发生的事件。
- 优先关注用户正在观察的人物、CP 与团体。
- 忽略无意义的睡觉、普通休息等流水账。
- 根据日报、周报、月报、季报、年报采用不同的信息密度与总结尺度。
- 关注角色之间的互动、关系发展与生活变化。
- 长周期报告应强调趋势，而不是简单罗列日期。
- 有意义的线下共同活动应获得适当篇幅。
- 不得将角色不知道的事情当成角色自身认知。
- 不要把观察者报告写成角色之间的聊天。
- 文风自然、清晰、具有适度的娱乐性。
- 禁止无意义的夸张赞美与凭空制造戏剧冲突。
- 所有重要结论应能够追溯到真实的事件或记忆来源。

报告允许使用合理的标题和段落格式。

此前“角色聊天禁止 Markdown”的全局规则，不应限制报告界面的富文本排版。

# 七、三个系统之间的联动

必须保证：

**观察范围决定详细模拟对象。**

**人物演化决定角色经历是否能长期改变其设定。**

**世界报告负责整理实际发生的事件。**

例如：

用户在世界 W 中只观察 A 与 B。

C 处于静默状态。

C 因特殊事件影响了 A。

系统应：

1. 生成 C 对 A 产生影响的必要事件。
2. 记录该事件。
3. 不因此激活 C 的全部生活。
4. 如果世界允许人物演化，判断事件是否可能长期影响 A。
5. 将有依据的变化写入 A 在 W 世界中的动态设定。
6. 在适当的日报或周报中呈现这件事。
7. 如果用户之后开始观察 C，回溯补全 C 的前三天生活。
8. 回溯内容不能与已经发生的 C 和 A 的互动冲突。

不能让三个模块独立生成互相矛盾的事实。

# 九、测试与验收

至少完成以下自动化测试：

### 测试 A：大型世界 Token 控制

创建 100 名角色、10 个团体。

只观察 5 名角色和 1 个团体。

模拟相同虚拟时间。

验证未观察角色不会大量生成无关聊天和生活事件。

与全量观察进行对比，确认 AI 生成任务数量明显下降。

### 测试 B：静默人物影响观察者

A 被观察，B 静默。

生成一个涉及 B 并影响 A 的重要事件。

确认：

- A 正确经历事件。
- B 只参与必要的部分。
- B 不因此进入完整模拟。
- A 的后续记忆和聊天能够引用该事件。

### 测试 C：避免观察范围级联

A 认识 B，B 认识 C，C 认识 D。

只观察 A。

确认 B、C、D 不因关系连接被自动全部激活。

### 测试 D：三天回溯

A 静默至少五个虚拟日。

用户开始观察 A。

确认至少向前覆盖三个虚拟日，并产生合理的历史内容。

再次观察时不会重复生成已有内容。

### 测试 E：回溯与现存事件一致

静默的 A 曾参与 B 的已知活动。

激活 A 并回溯。

确认不会生成与已知活动冲突的时间、地点及关系事实。

### 测试 F：世界独立演化

世界 W1 开启人物演化。

世界 W2 关闭。

同一个角色 A 属于两个世界。

W1 中发生事件导致 A 的长期行为倾向改变。

确认 W2 的 A 不受影响。

### 测试 G：设定锁定

角色存在锁定的核心人物设定。

触发多次演化评估。

确认核心设定不被修改。

### 测试 H：报告周期

使用虚拟日期测试日报、周报、月报、季报和年报。

包括：

- 普通跨日。
- 月末。
- 年末。
- 闰年。
- 五位数年份。
- 20× 高速模拟。
- 长时间离线恢复。

确认周期边界正确，且报告不会重复生成。

### 测试 I：报告事实一致性

生成事件后创建周报。

验证报告事实来自真实的事件记录。

报告不得产生新的生活事件。

### 测试 J：大量静默实体的性能

创建数百个静默角色。

模拟长时间运行。

确认调度复杂度、内存和 API 调用数量不会随静默人物数量近似线性爆炸。

### 测试 K：数据迁移

使用旧版 Demo 数据。

验证新功能升级后：

- 原有聊天不丢失。
- 已有世界仍能运行。
- 默认观察模式保留旧版体验。
- 新增报告开关不会意外启用。
- 原有角色设定不被自动重写。

# 十、开发与交付约束

请优先实现以下顺序：

1. 观察范围数据模型与 UI。
2. 活跃 / 静默模拟调度策略。
3. 与观察对象相关的重大事件机制。
4. 新观察对象前三天历史回溯。
5. 世界级人物演化开关和锁定机制。
6. 人物演化历史与可撤销操作。
7. 日报、周报、月报、季报、年报独立配置。
8. 报告生成与归档界面。
9. 三套系统之间的联动。
10. 性能测试、Token 使用测试及数据迁移验证。

不得通过简单隐藏聊天列表来伪装静默模拟。

**静默必须实际减少后台事件生成和 AI 请求，而不只是减少前端显示内容。**

不得通过删除现有历史来降低数据量。

不得为了补全三天记录而重复已有事件。

不得让 AI 自动修改用户锁定的核心角色设定。

不得让日报等功能成为新的高频 Token 消耗来源。

所有新功能必须兼容 PC、手机以及现有世界速度控制。

请直接完成增量开发、构建和验证，而不是仅提交设计说明。

**最终目标：即使一个世界拥有数百名角色，用户仍能够只观察自己喜欢的几个人或团体，同时保留其他角色作为真实存在的世界背景。随着虚拟时间推进，世界能够自然发展，而用户可以通过可控的人物演化和定期报告追踪值得关注的故事。**
