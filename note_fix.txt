# 二、P0-1：修复世界时钟偶发阻塞

## 2.1 当前问题

主界面显示的当前世界时间有时会停止更新。

不能先假设只是 React 组件没有刷新，也不能直接认定是后端卡住。

请调查从底层时间推进到 UI 显示的完整链路。

检查：

- Simulation Clock 的推进逻辑。
- 定时器和调度队列。
- AI 请求是否阻塞模拟流程。
- 大批量事件计算。
- IndexedDB 事务。
- 同步数据处理是否占用主线程。
- React 状态订阅和渲染。
- 长时间任务期间是否出现事件循环阻塞。
- 暂停和速度切换逻辑。
- 离线时间补全期间的状态管理。
- 页面切换及后台标签页节流。
- 多标签页之间的模拟控制权。
- 未捕获异常造成的定时任务停止。

请依据实际工程架构寻找根因，不要凭猜测修改某一个定时器。

## 2.2 架构要求

**世界时间推进、模拟事件执行、AI 内容生成和 UI 时间显示必须合理解耦。**

AI 请求耗时不应该直接阻塞世界时钟的显示。

生活事件生成失败也不应让整个模拟时间控制器永久停止。

推荐将以下职责分开：

1. Simulation Clock：计算虚拟时间。
2. Event Scheduler：安排待执行的模拟事件。
3. AI Task Queue：执行可能耗时的生成任务。
4. UI Clock Presenter：显示当前世界时间。

可以使用统一时间锚点计算虚拟时间，而不是简单地每秒累加一次状态。

计算应考虑：

- 最后一次时间锚点。
- 已经过的真实时间。
- 当前倍率。
- 暂停状态。

高负载或后台标签页定时器被节流后，应该依据实际经过时间进行校正。

不能因为一次定时器晚执行五秒，就永远丢失这五秒。

同时必须区分：

- 世界时钟已经推进到的时间。
- 生活事件实际执行并提交到的时间。

如果事件队列落后，允许世界时钟继续正常显示，但必须明确记录模拟任务积压情况，防止生成的事件时间戳与已展示的世界时间产生矛盾。

不得使用时间显示正常来掩盖模拟器实际上停止执行的问题。

## 2.3 UI 要求

正常运行时，时间显示应持续平滑或按合理精度更新。

如果出现：

- 模拟器暂停。
- 任务积压。
- API 等待。
- 数据恢复。
- 调度异常。

应显示对应状态，而不是无提示地冻结。

UI 时间更新不应依赖聊天消息到来或数据库写入才能触发。

不能因为聊天记录越来越多导致顶部时间控件不断重新渲染整个聊天页面。

## 2.4 调试和验证

开发期间增加必要的诊断日志：

- 当前模拟时间。
- 当前倍率。
- 最近成功调度时间。
- 任务队列长度。
- AI 任务状态。
- 数据提交延迟。
- UI 最近更新时间。

这些日志仅供开发调试，不能每秒无限写入本地数据库。

测试：

- 长时间正常运行。
- 连续触发 AI 请求。
- AI 故意延迟 30～60 秒。
- 一次性生成大量线下对白。
- 快速切换世界。
- 切换运行速度。
- 暂停后继续。
- 页面切换。
- 浏览器后台恢复。
- API 请求失败。

确认世界时间不会被无关 AI 任务永久阻塞，且调度器仍然正常运行。

# 三、P0-2：修复 AI 创建草稿频繁失败

## 3.1 当前错误

创建角色、团体或其他内容时，即使用户只在 AI 生成约束中输入少量简单要求，也经常出现：

“草稿格式仍不完整，已停止自动重试。请减少一次生成的人数或细节；预填写内容仍保留。”

这显然不能仅归因于用户提供的信息太复杂。

请排查实际原因。

## 3.2 排查范围

重点检查：

- AI 输出 JSON Schema 是否设计得过于复杂。
- 是否强制要求模型生成大量不必要字段。
- 是否错误地将可选字段判为必填。
- 是否存在递归或嵌套过深的数据结构。
- 输出 Token 限制是否不足。
- 是否存在 `finish_reason` 为长度截断的情况。
- 是否因模型输出额外说明导致解析失败。
- Structured Outputs 与当前 API 服务商的兼容性。
- 不同模型是否使用了不兼容的结构化输出参数。
- JSON 解析与业务字段校验是否混为一谈。
- 中文、日文文本或特殊字符是否导致错误。
- 是否有不合理的单次批量生成限制。
- 重试机制是否反复发送完全相同的失败请求。

需要记录内部可诊断的失败原因，而不是始终显示“草稿不完整”。

## 3.3 改进方案

采用宽容、分阶段的草稿创建流程。

例如：

**第一阶段：生成基本草稿**

只要求必要字段。

**第二阶段：自动补充可选字段**

人物介绍、性格、生活习惯、关系等信息可以后续生成。

**第三阶段：预览与编辑**

将已成功生成的字段交给用户确认。

不应要求 AI 一次性成功填写所有复杂字段才能创建内容。

### 用户只提供一句约束时

如果用户输入：

“请创建五个性格完全不同的高中女生。”

系统应能够自行生成基本草稿。

不能因为用户没有提供姓名、出生日期、关系网等信息就报格式错误。

这些可由 AI 合理生成或使用安全默认值。

## 3.4 结构化输出容错

需要支持：

- 可选字段缺失时补默认值。
- 允许生成部分成功。
- 可以逐个保存已完成的角色草稿。
- 仅对失败部分进行重试。
- 对截断响应进行合理处理。
- 对字段格式错误提供有针对性的修复。

不能用不安全的正则表达式随意拼接损坏的 JSON 并直接写入数据库。

所有修复后的数据仍需经过 Schema 校验。

对于不支持严格结构化输出的模型，应提供兼容的 JSON 解析与校验路径。

## 3.5 用户反馈

错误应区分：

- API 输出被截断。
- 响应格式错误。
- 字段内容不合法。
- 生成数量超过限制。
- 网络或服务商错误。
- 当前模型不支持所需输出模式。

并提供：

- 重试失败部分。
- 保留已有草稿。
- 手动完成创建。

不得将技术问题一概归咎于用户要求过多。

# 四、P0-3：修复线下对白预算超限

## 4.1 当前错误

线下观察经常出现：

“部分线下场景未生成：线下场景未保存：线下对白超出场景预算。已有的生活事件与聊天仍可查看。”

请彻底检查线下场景生成、预算计算、输出解析和保存流程。

## 4.2 必须排查

- 场景预算究竟按 Token、字数还是对白条数计算。
- 是否存在单位混用。
- 是否将活动说明也算入对白预算。
- 是否存在重复计数。
- 是否错误继承线上聊天的长度限制。
- 生成前预算与生成后校验是否不一致。
- 是否强制模型生成的对白数超过内部允许范围。
- 是否在生成完整场景后才发现预算不足。
- 是否因为单个阶段超限导致整个场景丢失。

## 4.3 新的预算策略

**线下场景预算必须具备自适应能力。**

不同场景应允许不同内容量。

例如：

- 短暂偶遇：少量对白。
- 午餐交谈：中等对白。
- 聚会：较多对白。
- 长时间约会：多个场景阶段。
- 排练或集体活动：阶段描述与对白结合。

预算应从场景规划阶段就考虑：

- 场景持续时间。
- 参与者数量。
- 场景重要度。
- 预期阶段数。
- 用户活跃度设置。
- API 总预算。

## 4.4 分阶段生成与保存

不要要求一次 AI 请求返回整个复杂线下场景。

推荐：

1. 规划场景阶段。
2. 生成第一个阶段。
3. 校验并保存。
4. 生成后续阶段。
5. 最终完成整个场景。

生成内容超出建议长度时，可以在不破坏语义和时间顺序的前提下拆分或重新生成部分内容。

如果受到硬性预算限制：

- 保存已通过校验的阶段。
- 标记剩余阶段未完成。
- 提供继续生成。
- 不丢失整个场景。

禁止因某个阶段对白过长就直接放弃保存所有线下内容。

## 4.5 输出校验

对话预算、时间范围、参与者身份和结构化格式分别校验。

对白稍长不应直接视为整个场景的数据结构损坏。

用户启用“不限制模型用量”时，应取消应用层的总 Token 预算限制，但仍保留必要的单次请求输出上限和安全校验。

必须实际验证线下场景能够稳定生成、分阶段保存及恢复。

# 五、P1-1：AI 生成人物关系网

现有关系网除了手动创建，也应支持 AI 自动生成。

## 5.1 入口

在世界关系图和角色关系编辑界面增加：

**AI 生成关系**

支持：

- 为单个角色生成关系。
- 为选中多个角色生成关系。
- 为指定团体生成内部关系。
- 为整个世界生成关系草稿。

用户可以输入补充要求。

例如：

“保持原作人物关系，另外让 A 和 B 关系更亲密。”

或：

“这些角色互相并不熟悉，只有两三个人是好友。”

## 5.2 生成规则

AI 需要参考：

- 角色资料。
- 所属作品。
- 当前世界规则。
- 团体关系。
- 既有关系。
- 用户额外约束。

允许生成：

- 关系类型。
- 双方熟悉程度。
- 双向亲近程度。
- 信任程度。
- 称呼与昵称。
- 对对方的态度。
- 关系背景。
- 共同经历建议。

**A 对 B 的感情不必等于 B 对 A 的感情。**

必须支持有向关系。

AI 生成结果必须先显示预览。

允许用户：

- 逐条接受。
- 批量接受。
- 删除建议。
- 修改参数。
- 重新生成某条关系。

用户已锁定的关系不得被直接覆盖。

AI 不确定的原作信息应标记为推测。

生成大量角色关系时，应分批执行，避免与当前草稿格式错误问题再次冲突。

## 5.4 手动修改

所有 AI 生成的关系必须能继续手动编辑。

修改应立即反映到关系图和后续 AI 上下文。

不得存在“AI 生成关系”和“手动关系”两套互不兼容的数据。

用户改为扮演 B：

- 点击 @ 名称打开对应人物资料。

支持：

- 回复预览。
- 引用原消息的发送者及摘要。
- 点击引用跳转原消息。
- 删除或修改原消息后的安全显示。
- 原消息不在当前加载范围时仍可正确定位。

不能简单复制文字，导致原消息编辑或删除后引用失去关联。

AI 生成回复时应能够得到被回复消息的必要上下文。

某条消息下显示：

点击可查看具体是谁回应的。

- 添加。
- 取消。

- 用户及 AI 角色回应。
- 存储回应者 ID。

回应不能只存数量，必须有可追溯的回应记录。

用户扮演角色进行回应时，应使用当前扮演身份。

同一角色对同一消息的同一种 Emoji 不应重复计数。

AI 可以偶尔对消息作出 Emoji 回应，但不能滥用，也不能因此无节制增加 API 调用。

## 7.6 谁已读、谁未读

增加可展开的消息阅读详情。

私聊：

显示对方是否已读以及模拟阅读时间。

群聊：

点击消息状态，可看到：

- 已读成员。
- 未读成员。
- 对应头像。
- 已读时间（如果有）。

必须区分：

1. 用户观察者阅读消息的状态。
2. 虚拟角色在世界中阅读消息的状态。

用户旁观一条消息，不等于所有虚拟角色都看到了这条消息。

虚拟角色的阅读事件必须由模拟系统决定。

例如：

角色 A 正在排练，B 在群里发了消息。

即使用户已经打开群聊，A 仍然可以保持未读，直到其实际有机会看手机。

已读详情应基于真实模拟数据，不能随机展示一个未经保存的已读列表。

对于尚未读到或加入会话之前的消息，需要合理定义可见范围。

# 八、P1-4：GIF 表情包系统

## 8.1 功能概述

新增 GIF 表情图库。

用户能够上传 GIF，并在私聊和群聊中作为图片消息发送。

GIF 应在支持的浏览器中正常播放。

支持：

- 上传。
- 预览。
- 命名。
- 删除。
- 搜索。
- 分类。
- 收藏或常用排序。
- 聊天输入栏快速打开图库。

第一版以 GIF 为主，不要求实现视频贴纸编辑器。

## 8.2 三层表情包配置

GIF 资源应支持三个层级：

**世界观共享表情包**

属于某个世界，世界中所有角色都能使用。

**团体共享表情包**

属于某个团体，该团体的成员在适用世界上下文中可使用。

**角色专属表情包**

属于某个角色，该角色可以使用。

有效表情包集合应由当前世界、当前会话上下文、角色身份共同确定。

优先级：

**角色专属 > 当前团体共享 > 世界观共享。**

这里的优先级主要用于同名、同标识或互相覆盖时的解析规则。

正常情况下，低层级资源仍应可见，不应因为角色拥有一个个人表情包就隐藏全部世界共享表情包。

当角色同时属于多个团体时，应根据当前会话的团体上下文及明确配置决定可使用范围。

禁止把角色所属所有团体的私人表情包无条件泄露到其他群聊。

## 8.3 AI 使用表情包

AI 角色也可以使用已授权的 GIF。

但不能将整张图片的二进制数据送进普通文本上下文。

建议为 GIF 保存：

- 唯一 ID。
- 名称。
- 情绪标签。
- 使用场景描述。
- 适用层级。
- 资源引用。

AI 只需要知道可用 GIF 的 ID、名称、描述与权限。

生成 GIF 消息时使用结构化资源 ID。

程序校验 ID 有效及角色有权使用后，再渲染实际资源。

不需要为了选择 GIF 强制调用图像识别模型。

## 8.4 GIF 文件存储

采用浏览器适合的 Blob / IndexedDB 资源存储方式。

不得将大量 GIF 以 Base64 形式塞入每条聊天消息。

需要：

- 文件大小限制。
- MIME 和文件内容校验。
- 去重策略。
- 本地持久化。
- 删除时的引用处理。
- 备份导入导出。
- 资源加载性能优化。

聊天历史中引用的 GIF 即使从图库移除，也应该采用合理的资源保留或缺失提示策略，不能导致整个聊天窗口崩溃。

支持用户暂停 GIF 自动播放或尊重系统减少动画效果设置。

# 九、P2-1：世界大型事件系统

## 9.1 功能定位

在世界观创建和编辑界面新增：

**大型事件（Major World Events）**

允许用户设置：

- 是否开启大型事件。
- 大型事件最大发生间隔。
- 大型事件发生倾向。
- 是否允许影响人物关系。
- 是否允许影响多个团体。

最核心的需求：

**用户可以设置虚拟世界经过多长时间，至少应该发生一次大型事件。**

例如：

- 每 3 天至少一次。
- 每 7 天至少一次。
- 每 30 天至少一次。
- 每 90 天至少一次。
- 自定义间隔。

可以提供天数输入框及常用预设。

使用虚拟世界时间，不是现实时间。

## 9.2 大型事件的定义

大型事件不意味着必须覆盖大量人物。

可以是：

### 少数角色之间的重要事件

例如：

- 两个人发生严重争执。
- 一段关系出现重大进展。
- 某人作出重要决定。
- 两三个人经历重大意外。
- 一次重要告白。
- 重要秘密被揭露。

### 团体级事件

例如：

- 乐队面临演出危机。
- 社团活动发生重要变化。
- 一场比赛。
- 一次内部冲突。
- 成员加入或退出。
- 某个共同计划取得成果或失败。

### 世界范围事件

例如：

- 大型庆典。
- 突发公共事件。
- 世界规则允许的特殊现象。
- 社会环境变化。
- 影响多个团体的重大事件。

事件必须符合世界设定。

普通校园世界不应该无缘无故出现超自然灾难。

## 9.3 大型事件发生间隔

必须实现有保证的调度机制，而不是简单依靠概率期待事件发生。

例如用户设置：

“每 7 个虚拟日内至少出现一次大型事件。”

系统应为下一个周期安排事件截止时间。

可以在周期内随机选择合理时机发生。

但是不能因为随机概率一直失败，就超过整个周期仍然没有事件。

建议保存：

- 上次大型事件发生时间。
- 下一次事件最晚发生时间。
- 当前计划事件时间。
- 已计划事件状态。
- 最近大型事件类型。

使用模拟时间调度。

暂停时倒计时停止。

倍速模式下正确推进。

离线补全应能够发现跨越的大型事件周期，并在历史补全过程中合理生成，不可直接跳过。

## 9.4 事件内容与频率限制

虽然设定了保证间隔，但不能机械地让每次事件都是灾难或巨大冲突。

应该综合考虑：

- 世界背景。
- 最近发生的事件。
- 角色关系。
- 团体状态。
- 当前生活阶段。
- 人物性格。
- 历史剧情连续性。

需要防止：

- 连续多次重复同一类型事件。
- 每周都有人分手或退团。
- 关系刚形成就突然崩溃。
- AI 无理由制造死亡或不可逆的重大变化。
- 强行改变用户锁定的人设。
- 团体没有经历过程就突然解散。

对于死亡、永久失踪、不可逆身份改变、删除团体等破坏性事件，第一版应默认禁止自动执行，除非用户明确开放对应权限。

重大事件可以影响感情与行为，但人物核心设定的永久改变仍应遵循世界观现有配置以及未来的人物动态演化规则。

## 9.5 生成与执行分离

大型事件建议分为：

1. 事件规划。
2. 参与者选择。
3. 时间与地点确定。
4. 前置条件校验。
5. 事件发生。
6. 线下场景或线上互动生成。
7. 状态与关系后果记录。
8. 后续影响安排。

AI 不能直接随意修改整个数据库。

需要通过结构化事件和程序校验提交结果。

重大事件应该具有可以持续影响后续生活的因果链，而不是出现一段描述后就再也没人记得。

## 9.6 与线下场景联动

重要事件通常可能带来更详细的线下互动。

例如：

某团体内部产生严重分歧。

应能生成：

- 事件发生。
- 多人现场讨论。
- 不同阶段的对话。
- 部分成员离开。
- 后续私聊。
- 必要的人物记忆。

但必须复用本轮修复后的分阶段线下生成机制。

不能因为大型事件的对白更复杂，又触发原来的场景预算超限问题。

## 9.7 不与日常事件混淆

大型事件应有独立的事件类型或重要度。

普通日常事件不能仅因数量较多就被认定为大型事件。

同时，普通事件如果自然发展成符合条件的重要事件，可以经过校验升级为大型事件。

这种自然产生的事件可计入当前周期的大型事件要求，避免重复强行安排。

同一个事件不得因不同来源而被重复生成。

# 十、P2-2：大型事件醒目通知

## 10.1 设计目标

大型事件是虚拟世界中值得重点关注的内容。

用户不能因为正在浏览其他页面，就错过重要事件。

但也不能使用无休止的强制弹窗破坏正常体验。

## 10.2 通知表现

发生大型事件时：

- 顶部出现醒目的游戏风格事件提示。
- 显示事件标题。
- 显示涉及人物或团体。
- 显示发生时间。
- 显示事件简介。
- 提供“查看事件”入口。

推荐采用与现有粗体、厚重轮廓的游戏化设计相符的特别通知卡片。

可以加入适度的入场动画。

不要使用夸张的大面积液态玻璃设计。

## 10.3 事件通知中心

增加大型事件通知历史。

至少包含：

- 未读大型事件。
- 已读大型事件。
- 按世界分类。
- 按发生时间排序。
- 按重要程度筛选。
- 跳转事件详情。

即使用户关闭提示，事件仍然保存在历史列表中。

可以在世界导航和首页显示大型事件未读角标。

## 10.4 重要事件详情

点击后可以查看：

- 事件标题。
- 发生时间。
- 发生地点。
- 参与人物。
- 相关团体。
- 事件经过。
- 相关线下观察。
- 相关线上聊天。
- 已确认的后续影响。

如果线下场景还没生成完成，应显示实际生成状态，并允许后续继续查看。

## 10.5 离线补全中的通知

用户关闭应用期间发生大型事件时：

重新进入世界后，离线补全完成应提示：

“你离开的这段时间里，发生了 X 件重大事件。”

展示对应的事件卡片。

不应对每个历史事件连续弹出多个阻塞式全屏弹窗。

应汇总展示，并允许逐条查看。

## 10.6 与世界暂停及倍率联动

高速模拟时可能连续发生多个大型事件。

系统必须：

- 正确保存每个事件。
- 防止通知重复。
- 合并适合汇总的提示。
- 保留全部事件历史。
- 允许用户之后阅读。

暂停状态下不得产生新的大型事件。

# 十二、强制测试项目

## 12.1 世界时间

模拟 AI 长时间请求和事件调度积压，确认 UI 时钟正常更新，模拟系统没有永久停止。

## 12.2 草稿生成

测试：

- 只输入一句生成约束。
- 生成单个人物。
- 批量生成五个人物。
- 不指定任何详细资料。
- 使用不同兼容模型。
- 响应被截断。
- 部分字段缺失。

应能正确创建或保留可编辑草稿，并提供真正有针对性的错误原因。

## 12.3 线下场景

测试长场景、多角色、多阶段、预算临界值、模型超长输出及中途失败。

确认不再因单个阶段超长而整场丢失。

## 12.4 AI 关系网

测试单人、双人、团体及世界级关系生成。

确认生成结果可预览、可编辑且不会覆盖锁定关系。

## 12.5 线上消息

验证：

- 第一条未读定位。
- 扮演身份切换后消息左右布局变化。
- @ 提及与角色 ID 关联。
- 引用回复跳转。
- Emoji 回应者明细。
- 群聊已读与未读成员详情。
- 观察者已读与虚拟角色已读相互独立。

## 12.6 GIF

测试世界、团体、角色三级图库的继承与覆盖。

确认未授权角色无法使用专属表情包。

测试图片存储、删除、历史消息引用和数据导入导出。

## 12.7 大型事件

模拟 30 个虚拟日。

将大型事件最大发生间隔设置为 7 天。

确认每个完整的 7 天窗口内至少发生一次符合条件的大型事件，或由自然产生的大型事件满足这一要求。

测试暂停、倍速、离线补全、重复任务恢复和通知。

## 12.8 回归测试

升级后原有数据不得丢失。

原本的：

- 角色资料。
- 世界观。
- 团体。
- 关系图。
- 线上聊天。
- 线下观察。
- 世界时间。
- 用户头像。
- API 配置。
- 全局提示词。

都应该正常工作。

# 十三、最终执行要求

请按顺序：

1. 排查并定位三个 P0 问题的真实根因。
2. 修改底层逻辑，完成修复。
3. 用故障注入与自动化测试确认不再复现。
4. 完成人物关系网和资源编辑能力。
5. 完成线上聊天交互升级。
6. 完成 GIF 多层图库。
7. 完成大型事件调度及通知。
8. 执行数据库迁移。
9. 进行 PC 和手机浏览器测试。
10. 完成构建与回归测试。

**必须先修复现有系统，再添加更多会加重模拟负载的新功能。**

不得以调低热闹度、缩短场景、减少角色或关闭 AI 自主交互作为 P0 问题的主要修复方案。

对于错误，必须定位实际来源。

对于新增聊天功能，必须使用结构化、可持久化的数据，不能只增加 UI 装饰。

对于大型事件，必须实现真正基于模拟时间的保证间隔调度，不能只依靠随机概率。

最后提供简明的开发报告，列出：

- 三项 P0 问题的根因。
- 已修改的关键模块。
- 新增功能。
- 数据迁移情况。
- 实际通过的测试。
- 仍然存在的已知问题。

不要把未验证的功能声称为已完成。

**本轮最终目标：让模拟世界运行稳定、聊天交互接近成熟社交软件、线下事件可靠生成，并让用户可以持续关注真正具有故事价值的大型事件。**
